Anthropic FlashProve：大模型的可证明推理

论文笔记 · 可证明推理

  • 来源：Anthropic Research 博客 + FlashProve 技术报告（开源项目）
  • 原文标题：FlashProve: An open-source library for provable inference
  • 原文链接：https://www.anthropic.com/research/provable-inference
  • 技术报告：https://www.anthropic.com/document/flashprove-technical-report
  • 代码仓库：https://github.com/anthropics/FlashProve （Apache 2.0）
  • 作者：Roy Rinberg、Alex Allain（Anthropic）；Alessandro Chiesa、Giacomo Fenzi、Guy Weissenberg（EPFL）；Miranda Christ（MIT）；Rahul Dalal（Anthropic / Succinct）；Ben Mayer（Anthropic / MIT）
  • 关键词：可证明推理 · zkSNARK · zkML · 零知识 · 形式化验证 · Lean · MoE
  • 整理日期：2026-11-09

一句话概括

以前你没法查证 AI 回复到底出自哪个模型；现在可以给每条回复附一张"数学收据"，几秒钟就能验证它确实出自那个模型，而且不泄露模型参数。Anthropic 把这个"收据生成器"的速度提升了几千倍，并把代码、形式化证明全部开源。

核心贡献不是新算法，而是把密码学（zkSNARK）、zkML 与工程优化"组合"起来——第一次让"证明一个 4000 亿参数大模型的推理"快到可用。

一、问题：你无法确认回复到底出自哪个模型

想象你打电话给一家公司，对方自称是"某某本人"，但你既看不见也摸不着，只能听声音。AI 就是这个状态。

你给模型发一句话，收到回复，但你没法确认：

  • 背后运行的真的是你指定或付费购买的那个模型吗？服务商可能为了省钱，悄悄换成小号或便宜模型。
  • 会不会有攻击者入侵服务器，冒充模型给你发回复（比如夹带恶意链接）？

光看回复的质量没用——便宜模型有时也能说得头头是道。

四个具体场景（原文的四类"挑战"）

场景具体担忧可证明推理能做什么
① 节奏控制（pacing）监管要求"算力只能做推理、不能偷偷训练新模型"，公司自己说了算，谁信？提交时段内推理请求的证明；监管者不用自建机房、也不用拿到权重即可核验
② 篡改检测服务器被入侵，或更先进的模型"顶替"被授权模型运行以绕过监控证明绑定到权重承诺；拿不到正确权重的证明就必然暴露
③ 文本溯源开发者宣称"我的代码经过某前沿模型扫描、烧了一百万 token 没找到漏洞"，用户怎么验证？每条输出附证明；可用"失败证明"（proof-of-failure）证明投入量
④ 模型审批监管只允许上线安全模型，公司有动机偷跑高风险模型强制附证明；用未获批模型则证明无法通过

⚠️ 原文明确承认场景①的边界：这只能证明"硬件在做推理"，不能证明硬件没有同时在偷偷训练。

为什么"公开权重"不是解法

原理上公开架构和权重就能验证，但：

  • 大多数提供方不愿公开权重（商业机密）；
  • 即便拿到权重，普通用户也算力不够——跑一遍模型就要 H100 级别硬件。

所以需要的是一种"我不会算，但我能查"的机制。

二、技术路线：zkSNARK 是什么

zkSNARK = 零知识简洁知识论证，拆开看三个词：

  • 零知识：验证者能确认"计算是对的"，但看不到模型权重和中间过程——模型还是个黑盒。
  • 简洁：一张收据只有几兆，验证只要几秒，不需要 GPU、不需要模型文件。
  • 论证：造假在计算上不可行（等价于破解底层密码学假设），所以验证者无需信任证明者。

流程分两步：

  1. 离线（一次）：服务商对模型权重生成一个很短的"指纹"并公布出去，等于公开声明"我承诺用这套权重"。权重本身是隐藏的。
  2. 在线（每次请求）：服务商给出回复，并附上证明："刚才那个被承诺的模型，在这个输入上确实会输出这些 token。"

任何人拿到「指纹 + 问题 + 回复 + 证明」，用普通电脑即可验证真假。

两条路线的对比：硬件 vs 纯软件

可信执行环境（TEE）纯软件密码学（本文路线）
安全依赖制造商做出防篡改硬件计算问题的困难性
环境被攻破安全性可能崩塌只要不破解密码学假设，仍无法伪造证明
是否需要信任厂商是否（透明设置）

原文立场：两者互补，各有不同的保证与权衡，都会在应对信任挑战中发挥作用。

五、证明系统的三层骨架

这是理解全文的钥匙。FlashProve 属于 STARK 这一支（虽统一叫 zkSNARK），由三层叠起来：

层内容解决什么
① IOP（信息论层）证明者发"很长的串"，验证者只做少量点查询让验证的工作量远小于计算量
② Merkle 承诺（BCS 变换）把"长串"换成短承诺 + 按需打开让验证者不必真的收下长串
③ Fiat–Shamir把交互折叠成一条消息变成非交互、可离线验证

关键取舍：第②③层是"正交的"，跟你要证明什么无关，可以直接复用。所以他们把工程量压在第①层——为 MoE 推理专门设计一个 IOP。

原文说法：系统的绝大部分只涉及信息论构造，非常适合自动化形式化和优化。

为什么选"只依赖哈希函数"

只依赖 BLAKE2 的表现像随机函数，不依赖椭圆曲线或格：

  • 好处：透明设置（无信任初始化仪式）、后量子安全、假设面最小。
  • 代价：证明更大更慢——这就是为什么是 19 MB 而不是几百字节。

论证逻辑：结构化假设（椭圆曲线、格）未来可能被算法攻击得更狠，而"哈希像随机函数"这个假设非常抗打。这是一条用效率换假设保守性的路线。

六、第一层：把"计算"变成"可抽查的编码"

IOP 的核心直觉，原文给了一个漂亮的类比：

纠错码之于信息，正如 IOP 之于计算。

  • 纠错码给消息加冗余，所以码字坏几个位置还能还原；
  • IOP 给计算加冗余，所以验证者只查几个位置就能判断一个大计算对不对。

为什么必须冗余？ 如果证明者老实把计算过程全发过来，验证者就得全读一遍，简洁性归零。冗余让"抽查几个点"就足以高概率抓住撒谎。

四个关键构件

① 零知识编码（ZK code）

证明者要先发"编码后的私有数据"（权重、轨迹）。但查询的答案会泄露信息——你问第 37 个位置，答案就跟你说了那里是什么。ZK 码的作用是：用随机性编码，使得有限次数的位置查询不泄露被编码消息的任何信息。

→ 这直接引出后面的大麻烦（查询预算），见第九节。

② Sumcheck（求和检验）

把"检查多项式在很多点上的和"归约为"检查它在一个随机点上的值"。

出现频率极高：每个请求约 2000 次 sumcheck，占全部交互轮次的 90–95%。用于折叠、查找子程序、以及把计算归约成线性声明。

换句话说，整个系统的节拍器就是 sumcheck。这也是形式化验证可行的原因——主循环简单得像 for 循环。

③ 折叠 + 跳转（fold and hop）

每轮归约后得到一条线性声明："向量 v 与编码消息 m 的内积 = y"。但这条声明跟计算一样大，不缩小就没有简洁性。所以：

  • 折叠：把多个"堆叠"的编码（code interleaving，交织码）用 sumcheck 压扁成一个小得多的编码，产出关于它的新声明；
  • 跳转：用 code switching 从一个码换到另一个码，目标是换到更适合小规模的码（"码率提升"）。

选 Reed–Solomon 码，因为编码快、且天生有好的零知识性质。这套思路与 FRI → BaseFold / Blaze / WHIR 一系最前沿工作同源。

④ 列表译码与域外采样（最不直观的部分）

邻近性参数决定效率：允许预言机离诚实码字有多"远"还能被接受。参数越大越高效，但分析越难。他们工作在列表译码区间——此时"离得近的码字可能有好多个"，所以需要：

  • 域外采样 把候选压成唯一一个；
  • 最前沿的 RS 码互相关一致性定理 来支撑分析。

这里是全篇最"吃数学"的地方：性能提升的一大半来自"把分析推到极限"，而不是代码写得好。

七、第二层：Merkle 承诺 = 可寻址的短承诺

矛盾很直白：直接发长证明 → 简洁性没了；让证明者自己回答查询 → 他可以撒谎。

解法：先承诺、后打开。 哈希树给长向量一个短承诺；之后要打开某个位置，就给出该位置的值 + 一条认证路径，对着承诺验证。

这解释了 19 MB 的来源：证明里塞的主要是打开的路径（Merkle 路径）和一些域元素，不是整个计算轨迹。

八、第三层：Fiat–Shamir 的 DAG 改造

这是全文最有意思的工程创新。

标准 Fiat–Shamir 是严格串行的：第 i 轮的挑战 = H(此前全部记录)，第 i 轮必须等第 i−1 轮哈希完成。

这和 GPU 是天敌。 单卡 H100 要同时跑几十个请求才喂得饱，但串行哈希链逼你一个一个来。

解法：把哈希链从"一条"改成"分叉再汇合的 DAG"

  1. 每个请求跑自己的前导段（分段、查找、约 2000 次 sumcheck），彼此独立；
  2. 所有请求关于权重的声明汇合到一个共享邻近性测试——汇合点是一棵基于各链末端值的小 Merkle 树，共享链从树根开始；
  3. 之后每条链再分叉回自己的收尾轮次。

效果：一个请求的串行哈希可以和另一个请求的重承诺工作在 GPU 上重叠。

本质是把"密码学协议的串行性"和"GPU 的并行性"对齐。

安全怎么补？逐轮可靠性

串行链里，一个挑战绑定它之前全部记录；DAG 里，一个挑战只绑定它依赖的分支。作弊者有了新自由度：

  • 先用 A 链的结果去挑 B 链的消息；
  • 或反复重抽某条分支

补丁：用一个更强的性质——逐轮可靠性（round-by-round soundness）：每一轮单独就"不会把假陈述变得更容易蒙混"，于是 DAG 的任意合法求值顺序都安全。他们为所有子协议都证了这个性质（带明确误差界），最终 IOP 继承它。

这是"协议安全性质的选择，被硬件执行模型倒逼出来"的典型案例。

九、"承诺-证明"带来的两个新麻烦

普通 zkSNARK 是"一次性"的：证一次，结束。这里不一样——权重承诺一次，之后几百万个请求都对着同一承诺证明。这打破了两条性质：

麻烦 1：绑定性与隐私要同时成立

  • 绑定：不能为"不是承诺的那套权重"出证明；
  • 隐私：承诺要能反复使用而不泄露权重。

麻烦 2：查询预算（最漂亮的一处设计）

一个 ZK 编码只有在被查询次数有限时才能隐藏消息。但每份证明都要读一批位置 → 读着读着预算就耗光了。

解法：链接证明（linked proofs）

  1. 先证"第一份编码是良构的"；
  2. 然后用新的随机性发出同一套权重的更多编码，每份附一个"与第一份编码持有相同权重"的链接证明；
  3. 请求的证明使用这些后续编码，于是没有任何一份编码被读超预算；
  4. 一个承诺能支撑的证明数 = 链接编码的数量。

→ 这就是"离线承诺约可用 1600 万次请求"的来源。

思路明确借鉴自基于哈希的签名里"一次性签名 → 多次签名"的提升（Merkle 树那套）。

十、zkML 侧：三个"顺着模型结构省钱"的决定

这一层是把密码学成本对准模型结构，而不是硬算。

① MoE 天生对证明者友好（最关键）

Llama 4 Maverick：128 个专家，每 token 只跑 1 个 + 1 个共享专家，4000 亿权重里只用 170 亿。

  • 证明者工作量可以和模型的实际工作量同阶，而不是按 4000 亿算；
  • 轨迹里只放被选中的专家的值 + 选择本身；
  • 检查选择：只需路由器那个小矩阵乘 + 一次比较，相对单个专家的矩阵乘很小；
  • 零知识怎么保：选择用指示向量表示，验证者把"被选专家的乘积"当成"所有专家按指示向量加权求和"来检查 → 它对权重的查询不依赖到底选了哪个专家。

这是全文技术密度最高的地方之一：同时解决了"省算力"和"不泄露选了谁"两个目标——因为"选了谁"本身就泄露权重信息。

② 量化让整数运算 = 域运算

IOP 工作在有限域 F_p 上。只要所有值一直落在 [0, p) 内，整数运算和域运算就完全一致。

→ 代价：你得全程保证值不越界，还得让验证者相信它没越界（→ 范围检查，见第十一节）。

③ 查找表处理非线性

softmax、SiLU、ReLU、比较这些，用域上算术表达极贵。查找协议的思路是：非线性函数公开已知，像三角函数表一样写下来，证明者只需声称"我每个 (x, f(x)) 都是表里的一行"。

→ 表必须小，否则复杂度爆掉。所以他们对输入做了截断：SiLU 超出范围就截断，softmax 的指数舍入到零。

十一、真实实现与"教科书版"的三处偏离

原文很老实地列了简化版和实际版的差别。每条都是拿安全/简洁换工程可行性：

① 批处理（省查询预算）

  • 简化版：一个请求，对权重编码做一次邻近性测试。
  • 实际版：一批请求一起证，各自保留自己的轨迹预言机和归约，但关于权重的声明合并，于是每批只打开一次权重承诺。
  • 好处：对编码的查询次数大幅下降，这对 ZK 查询预算至关重要。
  • 且每个客户端只收到自己那部分 + 共享部分，连"这批有几个请求"都不泄露。

② 分段（这是"单卡"的核心）

  • 简化版要把整条轨迹 + 编码一直握在手里 → 远超一张 GPU 的容量。
  • 实际版把层切成段：发一段的轨迹、归约它的声明、只把下一段需要的少量值往前传 → GPU 内存里一次只有一段。
  • 代价：轮次变多，各段依次证明。

③ 近似范围检查（最诚实的一处妥协）

  • 简化版：轨迹每个值做一次查找。太贵。
  • 实际版：检查整个矩阵条目的随机和。
  • 代价是完备性不完美：诚实值之和可能偶然很大，诚实证明者偶尔被拒（概率极小）。
  • 更麻烦的是：被拒的请求可能泄露权重信息（因为"被拒"本身就是个信号）。补丁是换随机性重试；原文明确写"计划在未来版本解决"。

⚠️ 值得注意：零知识性在这里不是"证明过的性质"，而是"用重试维持的工程性质"。

十二、Lean 形式化：证明了什么、没证明什么

这决定整套东西的可信度边界。

证明了的（Lean 里机器检查）

  1. 一个形式化关系 R，刻画"给定模型的全部正确推理计算"；
  2. 三个性质：完备性、可靠性、零知识性，在随机预言机模型（ROM）里，带明确误差界；
  3. 协议本身（证明者函数、验证者函数）；
  4. 主定理："该协议是 ROM 中 R 的论证系统，完备性误差 ≤ ε₁、可靠性误差 ≤ ε₂、ZK 误差 ≤ ε₃"。

没证明的（信任缺口）

  • C++/GPU 代码与 Lean 规范不等价，且证明者代码是 AI 从 Lean 生成的；
  • 技术论文本身是 AI 写的、未详审（原文自己写明）；
  • Lean 内核 + 编译器要信任；
  • 批量请求的零知识性还没证明（单请求已证）。

一个漂亮的非对称性（整套设计的"支点"）

性质只需信任谁代码出错会怎样
可靠性只有验证者证明者代码出错不影响可靠性
完备性双方诚实（非对抗）出错 → 诚实证明被拒（可用测试发现）
零知识性只有证明者出错 → 可能无意泄露权重

所以："只要信任验证者，就完全不需要信任证明者"——这正是 zk 的全部价值。

为此他们提供两个验证器：

  • C++ 版（快，日常使用，无形式化保证，但测试中与 Lean 版逐份判定一致）；
  • Lean 版（慢，但被证明"只接受可靠性定理里那个验证者所接受的内容"）。

ZK 这块他们直接放弃辅助：证明者太贵，跑 Lean 版不现实，所以"希望隐藏权重的证明者，自己有钱做人工/智能体审计"。

一句话：可靠性有数学保证，完备性靠测试，零知识靠自觉 + 重试。

十三、性能数字怎么读

别被"110 倍"误导。

指标数值怎么理解
吞吐110 tok/s批处理下的处理速率，不是单请求延迟
单请求延迟约 5 分钟（等整批证明发布）因为"没人在等证明"→ 事后证明
若改成逐个证单份 58 秒就绪，但吞吐掉到 17.6 tok/s延迟 vs 吞吐的经典权衡
开销72 倍（66–77），高负载 94 倍对 vLLM 的预填充、按每张 GPU 计
验证24 线程 17 秒 / 单线程 21 秒含离线阶段检查，不需要 GPU
下载量承诺 + 离线证明 + 链接共 6.24 MB一次性
离线阶段39 分钟，存 2.15 GB每模型一次，摊到 1600 万次请求 ≈ 可忽略

三个容易误读的点

  1. "110 tok/s"是和"vLLM 预填充"比的，不是和完整服务比。

他们刻意选了预填充（计算受限、高度可并行），因为事后证明只需重算一次前向传播。真实服务的解码阶段是带宽受限、串行、效率低得多——所以"70–95 倍"这个分母其实是个对 vLLM 很有利的分母。

  1. 检查每个 token 和不检查，速度几乎没差别（若只算被检查的 token，为 39.1 tok/s）。所以"一份证明只查一个 token"是测量口径，不是能力上限。
  1. 批大小上限 64，实测用 24。

十四、事后证明：省了 99%，但放弃了"阻止"

为什么事后证明几乎免费？

  • 重算一次前向传播的代价 ≈ 1 次推理；
  • 证明的代价 ≈ 70–95 次推理；
  • 所以重算只给证明者增加 1%–1.5% 的工作量。在线证明省下的那点重算，完全不值得。

更重要的是解耦：证明比推理贵一两个数量级，若同机运行会抢内存和带宽，直接伤害用户体验。用推理工程的术语说，这让团队可以专注优化证明预填充（可并行、计算受限），而非解码（串行、带宽受限）。

代价（原文讲得很坦率）

  1. 只能"发现"，不能"阻止"。用户先拿到回复，证明后补。所以"已篡改但会被发现"这件事，对已经中毒的用户没有意义。
  2. 泄露型攻击仍可能成功：攻击者可以在"证明失败 → 运维发现服务器被入侵"这个信号发出之前，通过一条被篡改的回复泄露关键比特。
  3. 必须信任日志：攻破日志的对手可以"日志里记模型的正确输出，实际发你篡改的输出"。

所以他们把事后证明定位为纵深防御的一层，不是替代品。

十六、批判性评价

真突破（我认为可信）

  1. 把"4000 亿参数模型的推理证明"从"小时/GB 级"压到"秒/兆级"——这是可用的门槛线；
  2. DAG 化 Fiat–Shamir：把密码学前言的串行性和 GPU 并行性对齐，思路可迁移到其他 zkML 系统；
  3. MoE 的指示向量技巧：同时拿到效率和零知识，是真正的结构洞察；
  4. 以 Lean 为"单一事实来源"，由它导出论文和代码：方法论样本，比结果更有价值；
  5. 全开源 + 明确标注"AI 写的、未审"：这种自我披露在业界很少见。

薄弱环节（部署前必须解决）

  1. "证明的模型 ≠ 服务的模型"。

证的是整数 + 贪心；线上是浮点 + 采样。这不是"小噪声"，而是在某些位置是不同的函数。现实威胁模型里，攻击者恰恰会挑这些位置。统计方法能区分良性数值噪声与篡改，但这是统计，不是证明——严格说，这一步把"可证明"降级成了"可检测"。

  1. 架构不隐藏。 对"监管者能查、但别偷我 IP"这个用例，只藏权重不藏架构不够。
  1. 1024 token 上下文。 和真实聊天差两个数量级，而证明成本随上下文增长，外推并不平凡。
  1. 无多卡/张量并行。 对生产环境拓扑是硬约束。
  1. argmax 检查的细节被略过。 要证明"这个 token 是词表里得分最高的"，需要在 20 万词表上做比较/最大值论证，而比较是非线性的 → 得靠查找或排序置换论证。这块的成本和安全性，报告没展开，值得追问。
  1. "批量 ZK 未证" + "近似范围检查牺牲完备性"：两处都在系统最敏感的性质上开了口子。
  1. 安全目标 128 比特，但误差界的具体数值要自己核。 正文只写"这里 ε 是具体的小数"，看代码/Lean 才知道真实参数。

十七、结论

这篇文章真正证明的不是"AI 安全"，而是"AI 供应链可审计"在技术上可行：你可以用一张 19 MB 的数学收据，证明某句话出自某套被承诺的权重——而在这之前，这件事被认为要花上几天和 90 GB。

但它同时暴露了这条路的边界：

  • 能证明"哪个模型跑的"，证不了"模型对不对、安不安全"；
  • 能发现篡改，阻止不了；
  • 当下证的是"一个和线上模型很接近但不一样的东西"。

如果只记三句话

  1. 哈希 + 折叠式 IOP + 批处理，把证明成本从"几小时"压到"每秒百 token"；
  2. DAG 化 Fiat–Shamir + 链接证明，解决了"GPU 并行"和"一个承诺复用于千万请求"这两个真实部署障碍；
  3. Lean 钉死了可靠性，但代码等价性、批量 ZK、浮点一致性都还是开的——所以它是里程碑，不是终点。

一个容易被忽略的伏笔

原文脚注提到：2026-10-19 的 RSP 更新里，Anthropic 把目标名称从"可证明推理"改成了"推理验证"（inference verification），因为最初的目标只是"对自身 token 流获得高度保证"，而密码学证明只是多种实现方式之一（他们另有一个"签名 + 可信服务器重算"的项目已达到该目标）。

读这篇时要分清：FlashProve 是"另一条路的技术演示"，不是 Anthropic 生产合规方案的唯一答案。

十八、术语速查

术语一句话解释
zkSNARK零知识简洁知识论证：证明者用一条短信让验证者确信某计算做对了，且不泄露别的
IOP交互式预言机证明：验证者只能"点查询"证明者的长串，是整栋楼的地基

Fiat–Shamir用哈希把交互"折叠"成单条消息，得到非交互证明
Merkle 承诺哈希树：给长向量一个短承诺，可按位置打开
Sumcheck把"很多点求和"归约为"一个随机点的值"，系统的主要节拍器
折叠 / 码切换逐步缩小声明规模、在码之间跳转，是简洁性的来源
列表译码区间邻近性参数开到极限的分析区间，效率最高但最难证
完备性 / 可靠性 / 零知识真陈述必被接受 / 假陈述难以取信 / 不泄露额外信息
MoE混合专家：每 token 只激活少数专家，4000 亿里用 170 亿
指示向量用 0/1 向量表示"选了哪个专家"，让查询不泄露选择
查找论证用公开小表处理非线性函数，避开昂贵的域上算术
Lean证明助手，把定理写成代码并由机器检查
DAG Fiat–Shamir本文把哈希链分叉成有向无环图，换取 GPU 并行
链接证明用同一权重发出多份编码并互证，绕开单份编码的查询预算
